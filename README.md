# Kafka-кластер KRaft с помощью Ansible

Готовое тестовое задание: Ansible Playbook устанавливает кластер Apache Kafka из трёх узлов в режиме KRaft, без
ZooKeeper. Kafka запускается как системная служба systemd на Linux-серверах или виртуальных машинах.

## Что делает это решение

```text
Приложение → Kafka → ClickHouse → аналитика и отчёты
```

Приложение отправляет в Kafka события: регистрации, клики, покупки и другие действия пользователей. Kafka временно
хранит события и передаёт их потребителям. ClickHouse читает события из Kafka и сохраняет их для аналитики.

Playbook автоматически:

- устанавливает Java и Kafka;
- объединяет три сервера в отказоустойчивый кластер;
- настраивает шифрование TLS и вход по SASL/SCRAM;
- создаёт отдельных пользователей для приложения и ClickHouse;
- ограничивает их права с помощью ACL;
- запускает Kafka через systemd;
- безопасно выполняет последовательные обновления;
- проверяет отправку и получение тестового сообщения.

## Архитектура

```text
Приложения -- SASL/SCRAM + TLS --> [Kafka 1] ----+
                                     [Kafka 2] -----+--> ClickHouse
                                     [Kafka 3] ----+
                                       KRaft-кворум
```

Все три сервера одновременно выполняют роли broker и controller. Для небольшого кластера это разумный компромисс:
решение выдерживает отказ одного сервера и не требует дополнительных машин. Для большой нагрузки лучше использовать
три отдельных controller-узла и независимо масштабируемые broker-узлы.

По умолчанию данные имеют три копии (`replication.factor=3`), а для подтверждения записи нужны минимум две копии
(`min.insync.replicas=2`). Producer должен использовать `acks=all`.

Используется Kafka 4.3.1 с зафиксированной официальной контрольной суммой SHA-512. KRaft заменяет зависимость от
ZooKeeper. Java 17 устанавливается из репозитория операционной системы.

## Безопасность

- Все соединения шифруются с помощью TLS.
- Внутренние узлы взаимно проверяют сертификаты друг друга.
- Клиенты входят по логину и паролю SCRAM-SHA-512.
- По умолчанию доступ запрещён, необходимые разрешения выдаются через ACL.
- Producer и ClickHouse используют разные учётные записи.
- Пароли хранятся в Ansible Vault и не попадают в Git.
- Kafka работает от отдельного системного пользователя без возможности входа в shell.

## Требования

- управляющий компьютер с Linux/macOS или WSL, Python 3 и Ansible Core 2.15+;
- три Linux-сервера с systemd: Debian/Ubuntu или RHEL-совместимая система;
- рекомендуется минимум 2 CPU и 4 ГБ RAM на сервер;
- SSH-доступ с возможностью использовать sudo;
- рабочие DNS-имена для каждого `kafka_advertised_host`;
- сетевой доступ между Kafka-узлами на TCP 9092 и 9093;
- доступ клиентов к TCP 9094.

Адреса в примере предназначены только для документации. Перед запуском их обязательно нужно заменить.

## Структура проекта

```text
site.yml                         главный сценарий установки
verify.yml                       проверка кластера и тестового сообщения
requirements.yml                 необходимые коллекции Ansible
inventories/example/hosts.yml    адреса трёх серверов
inventories/example/group_vars/  настройки Kafka и пример секретов
roles/kafka/tasks/               шаги установки и настройки
roles/kafka/templates/           конфигурация Kafka и systemd
```

## Как развернуть

Сначала нужно создать файл с секретами:

```bash
cp inventories/example/group_vars/vault.yml.example inventories/example/group_vars/vault.yml
```

Затем заменить тестовые адреса и пароли:

```bash
$EDITOR inventories/example/hosts.yml
$EDITOR inventories/example/group_vars/kafka.yml
$EDITOR inventories/example/group_vars/vault.yml
```

Зашифровать файл с паролями и запустить установку:

```bash
ansible-vault encrypt inventories/example/group_vars/vault.yml
ansible-galaxy collection install -r requirements.yml
ansible-playbook site.yml --ask-vault-pass
ansible-playbook verify.yml --ask-vault-pass
```

Сгенерированный центр сертификации и ключи узлов сохраняются на управляющем компьютере в `.generated-pki/`. Папка
исключена из Git. Её следует хранить в защищённом хранилище резервных копий. В рабочей инфраструктуре локальный центр
сертификации лучше заменить на Vault PKI или корпоративный CA.

`kafka_cluster_id` — идентификатор кластера, а не пароль. Он создаётся один раз командой
`kafka-storage.sh random-uuid` и не должен изменяться для уже существующего кластера.

## Подключение ClickHouse

Автоматическое создание топиков отключено. Рабочий топик нужно создать явно, например:

```bash
/opt/kafka/bin/kafka-topics.sh --bootstrap-server kafka-1.example.internal:9094 \
  --command-config /etc/kafka/admin.properties --create --topic user-events-v1 \
  --partitions 12 --replication-factor 3 --config min.insync.replicas=2
```

В ClickHouse необходимо указать:

- адреса всех трёх Kafka-брокеров;
- consumer group `clickhouse-main`;
- пользователя `clickhouse` и его пароль из Vault;
- протокол `SASL_SSL`;
- механизм `SCRAM-SHA-512`;
- сертификат центра сертификации кластера.

Рекомендуемая схема ClickHouse: таблица Kafka Engine → materialized view → таблица `ReplicatedMergeTree`.
Начать можно с формата JSONEachRow. При активном развитии схемы событий лучше использовать Avro или Protobuf вместе
со Schema Registry.

В каждое событие полезно включать `event_id`, `event_time`, `user_id`, `event_type`, `schema_version` и `payload`.

Доставка Kafka → ClickHouse обычно работает по принципу «как минимум один раз», поэтому возможны повторные события.
Для защиты от дублей следует использовать `event_id` и, при необходимости, `ReplacingMergeTree` или отдельный этап
дедупликации. Если важен порядок действий пользователя, Kafka-топик следует разбивать по ключу `user_id`.

## Эксплуатация

- Для обновления измените версию и SHA-512, затем снова запустите `site.yml`. Параметр `serial: 1` перезапускает узлы
  по одному и сохраняет доступность кластера.
- Пароли клиентских пользователей можно менять через Vault. Изменение bootstrap-пароля администратора требует
  отдельной согласованной процедуры.
- `verify.yml` проверяет KRaft-кворум, создаёт временный топик и отправляет через него JSON-событие.
- Нужно отслеживать недореплицированные партиции, состояние ISR, задержки, место на дисках, JVM, controller,
  consumer lag и ошибки загрузки ClickHouse.
- Kafka следует рассматривать как буфер повторного воспроизведения, а не как единственное постоянное хранилище.
- Для аварийного восстановления между дата-центрами лучше использовать второй кластер и MirrorMaker 2.

## Что намеренно не входит в проект

Playbook не создаёт виртуальные машины, DNS-записи, сетевые правила, ClickHouse или Schema Registry. Эти компоненты
зависят от конкретной инфраструктуры. Проект также не открывает Kafka в публичный интернет. Для реального запуска
нужно указать настоящие Linux-серверы, настроить DNS, сетевой доступ и секреты.
